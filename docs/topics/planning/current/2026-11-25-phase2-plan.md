## 0. Ground rules

- **Read-only setup.** `git fetch origin`; the planning worktree was added with
  `git worktree add --detach /root/dev/worktrees/phase2-plan origin/master` and stopped short if
  that path had existed. The docs branch is `phase2-plan-docs`, created from
  `origin/phase1-plan-docs`. The implementation stack is **not** based on that docs branch and
  **not** on `master`: it is based on Phase 1's top branch **`phase1-league-group-fk`** (§2).
- **Phase 1 is a prerequisite, not a backdrop.** Phase 1 Layer 4 (`phase1-snapshot`) adds
  `liveticker/service/gamedays_hooks.py` and changes `liveticker/apps.py`; Phase 1 Layer 6
  (`phase1-api-context`) changes `gamedays/api/game_views.py` (the passcheck annotation becomes a
  hook). Phase 2 Layers 3, 5 and 6 touch those same files. Rebase onto the implemented Phase 1
  top, keep its hook calls intact, and treat any conflict as a Phase 1 change to preserve — never
  as a line to revert (Phase 1 plan §§5,7).
- All commits signed (`git commit -s`), conventional, one logical change each. PRs are a `gh
  stack`, **ready for review (`--open`), never drafts**. The agent **never merges**; the user
  merges bottom-up (roadmap:77; Phase 0 plan:11-12).
- Required CI contexts: `full_gate`, `scope_coverage`, `check_version_sequence` (Phase 0
  plan:13). `python3 scripts/check_scope_coverage.py` must pass after every layer that adds
  tracked files. Every new doc is excluded (`.circleci/scope-exclude.txt:8-9`); new `scripts/**`
  files are covered by `(tests|scripts)/.*` (`.circleci/scope-mapping.txt:95`). No scope-mapping
  change is expected.
- **100% branch coverage** of every new module and every function created, changed or moved,
  enforced by `scripts/check_branch_coverage.py` (Phase 1 Layer 1; absent from `master` at
  planning time). Characterization tests must prove 100% of the original functions **before**
  any removal or move (`--base HEAD --require-file … --require-function …`), then the
  diff-scoped gate must be green again after the change. Ownership: `gameevents`/`gamedays` →
  `python-gamedays`, `liveticker` → `python-live`, `scripts` → `python-cross` (Phase 1 plan §2.2).
- **Query counts pinned** with `assertNumQueries` on every changed DB-touching function; counts
  must not grow (root `AGENTS.md:205-211`). Removal layers may *reduce* a count — pin the new
  number explicitly. `check_game_projection --all` stays at five queries plus one legacy count
  (`check_game_projection.py:9-12,76-86`).
- **No schema migrations.** `Gameinfo.event_source` stays unimplemented; §9.1 designs around it
  with the existing `GameEvent.source` column. A migration would break the shared-DB ref/cand
  model (roadmap:38) and would force a second DB copy; that is explicitly **not recommended**.
- **Stage, ref and cand.** `ref` remains the programme baseline `agent-ref` at master
  `96ec02b175a62e0e264f51771355ebf806c21797` for the whole programme; `cand` is rebuilt from
  each layer head into `agent-candidate`. Do not re-run `ls.app.stage` or `ls.db.sync` during the
  phase (Phase 0 plan:176,182). Do not hand the agent prod or public-stage access.
- **Equivalence is mandatory for every layer.** First ref-vs-ref noise floor (all four harness
  role credentials present), then flag-OFF cand vs ref: **zero diffs** on every probe and
  scenario. Layers 4–6 additionally run the flag-ON comparison described in §6. A diff is a bug
  unless declared intended with a reason in the PR body and via `--intended`; `runner.py` exits
  non-zero on anything unexplained (`:157,168-171`). Reports are redacted (README:49-54).
- **Merge safety.** Every layer except the last two is **safe to merge with prod's flag OFF**:
  it cannot change prod behaviour while `SCORECARD_EVENT_FEED=false`. The last two are explicitly
  **MERGE ONLY AFTER GAMEDAY REHEARSAL** (§8.3) and stacked last: the user runs a full simulated
  gameday on the agent stage on `ref` vs `cand`, with `check_game_projection --all` clean and the
  `scorecard_v2` e2e scenarios passing. There is **no prod soak**. Flag rollout on
  stage/demo/prod is an Ansible step in the separate `dachrisch/servyy-container` repo and is
  **pending, user-gated**; the agent only plans the servyy-test part.
- Module guides are authoritative: root `AGENTS.md`, `gamedays/AGENTS.md`, `liveticker/AGENTS.md`,
  `scorecard_v2/AGENTS.md`, `league_manager/AGENTS.md`. There is **no `gameevents/AGENTS.md`** at

## 4. Layer 2 — `phase2-reconciliation-report` (~200 lines; safe to merge with flag off)

**Goal:** make "zero unreconciled v2 games; legacy set explicitly accepted and documented"
measurable and reproducible, before any cutover code is touched.

**Files:** modify `gameevents/management/commands/check_game_projection.py` (add `--report`),
new `gameevents/service/report.py`, new tests under `gameevents/tests/management/` and
`gameevents/tests/`, new
`docs/topics/planning/current/2026-11-25-phase2-legacy-acceptance.md` (+ README line), extend
`docs/topics/guides/scorecard-events-operations.md` with an "Accepted legacy set" section.

**Approach:**
- Extend the existing command with `--report <path>` (no new command, no new query): reuse
  `check_games()` (`reconcile.py`, five queries for `--all`) and write a JSON report with
  `{generated_at, ref_sha, cand_sha, event_games, ok, drift, flagged, by_source: {v2, legacy,
  staff}, legacy_without_events, shadow_only, legacy_cutoff, legacy_without_events_digest,
  per_season}`. Each drift/flagged entry carries the game's `source`; `v2_drift` and
  `v2_flagged` are the gates. The digest is SHA-256 of the sorted ids of the **whole accepted
  set** (no-event and shadow-only games), restricted to ids at or below the recorded
  `--legacy-cutoff`; the cutoff makes the digest reproducible as new v1 games appear. Exit
  status and stdout stay byte-compatible; `--report` is additive.
- Classify by `GameEvent.source`: only `v2` games must be reconciled; shadow-only (`source=legacy`)
  games and no-event games are part of the accepted legacy set. This makes the eventual cutover
  discriminator (§9.2) measurable now without changing behaviour.
- Commit an acceptance record: definition of the legacy set, the count and digest observed on
  the agent stage, per-season counts, the cutoff, the exact command to regenerate, and the
  explicit statement that **no backfill will be performed**. The record is written from a real
  stage run of `check_game_projection --all --report …` on `cand`, not from memory. The stage
  has zero shadow-only games, so the changed set definition does not change the recorded values.
- No schema change; no production read path changes. **P3, approved 2026-11-26** (§11): store the
  digest + counts, not the raw ids, in the public repo.

**Tests first (two commits):**
1. Characterization: pin the current `--all` stdout, exit codes, five-query count and legacy
   skip count; verify 100% branch coverage of the original `handle`/`_legacy_games` with
   `--require-file/--require-function` before editing.
2. Report tests: `report.py` grouping by source, fixed SHA-256 of the empty set, digest stability
   under id order, shadow-only games included in the count/per-season/digest, source on every
   drift/flagged entry, `v2_drift`/`v2_flagged`, cutoff filtering, CLI `--report` writing valid
   JSON and leaving stdout unchanged, query count unchanged; plus a DB-backed test of the source
   derivation for a shadow-only game and a v2 game; then the diff-scoped gate back to 100%.

**Coverage / queries:** `python-gamedays` shard; `assertNumQueries(6)` for `--all` (five + legacy
count) unchanged; report generation does zero extra DB queries.

**Equivalence:** flag OFF — zero diffs (management command is not a probed surface). Flag ON —
run the full comparison after generating the report; zero diffs required, and the gate is read
from `v2_drift == 0` and `v2_flagged == 0` in the report, not from the command's exit code (a
shadow-only game can be flagged without failing v2). If a sampled game is flagged, repair the
stage data with `rebuild_game_projection --game <id>` (data only, never a code change), re-run the
noise floor, and record the repair in the PR body.

**Risks / rollback:** a report that silently counts shadow games as v2 would fake success — the
`by_source` assertion in tests prevents it. Rollback = revert PR; the command reverts to its old
stdout-only contract. **Merge safety: safe to merge with prod flag off.**

## 5. Layer 3 — `phase2-equivalence-coverage` (~250 lines; safe to merge with flag off)

**Goal:** extend the harness so the four Phase 2 surfaces are actually exercised, and make
intended diffs possible for the two cutover layers.

**Files:** `scripts/equivalence/manifest.json`, `scenarios.py`, `runner.py`, `report.py`,
`README.md`, tests in `scripts/equivalence/tests/`; no app code.

**Approach:**
- `manifest.json`: add anonymous probes `/api/liveticker/` (json) and `/liveticker/` (html) for
  sampled designer/canvas/completed gamedays; add a sample `/api/game/{game_id}/feed` probe by
  extending discovery with one game id per sampled gameday (reuse
  `/api/gamedays/{gameday_id}/games/`). Exclude `/api/liveticker/stream/` (SSE is not diffable).
  Add an `If-None-Match` revalidation probe for both liveticker and feed: literal validators stay
  normalised noise (`normalise.py:50-66`), but a changed validator must flip the response between
  200 and 304 identically on both sides. Each revalidation probe references its own expanded
  source name (`base#category:id`), never a bare base name, so it revalidates its own sample;
  report a probe that never receives a 304. Phase 1 Layer 1 already added snapshot/ETag probes
  — extend, do not duplicate (Phase 1 plan §2.5).
- `scenarios.py`: add three scenarios with run-id-tagged entities and run-id-derived UUID
  `client_id`s (add them to `id_tokens` so they normalise):
  - `v2-events-write`: create/publish/read games → `POST /api/game/{game_id}/events` with an
    `events` envelope (`type=score`, `code=touchdown`, `side=home`, `player`, `period=1`, shared
    `client_id`; shape per `gameevents/api/serializers.py:3-12,118-140`) → read feed, gamelog,
    liveticker.
  - `v1-shadow-write`: same setup → `POST /api/gamelog/{game_id}` with a run-id client id →
    read gamelog, feed, liveticker. This is the shadow path at `game_views.py:310-323`.
  - `reconciliation-flag`: setup must first write a **sequence-0** row (`Strafe`, whose rows
    intentionally share sequence 0 via `gamelog.EXCLUDED_EVENTS`) in addition to the touchdown;
    `DELETE /api/gamelog/{game_id}` with `{"sequence": 0}` then finds that row and reaches the
    flag branch at `gameevents/service/undo.py:104-109`. Deleting only the touchdown (sequence 1)
    returns early at `:91-93` and never flags anything. Read the feed expecting **409** with
    `needs_reconciliation: true` on **both** sides, and the liveticker expecting the row fallback.
    Assert that contract per side in the harness, and show it in the report; a step-name-only
    test cannot catch a no-op delete.
- **Runner fix (needed by Layers 5–6):** apply `report.py::split_intended` to scenario diffs as
  well, keyed `<scenario>:<step>` (e.g. `v1-shadow-write:read-feed`); make `runner.py:157` fail on
  *unexplained* scenario diffs only, resolve a scenario's status from the `<scenario>:` key
  prefix (not an exact key lookup, which always prints "clean"), and render declared scenario
  diffs in the "Intended diffs" section. Without this, `--intended` cannot cover the deliberate
  diffs in Layer 5.

**Tests first (two commits):** characterize the current runner exit codes, report sections,
manifest expansion and scenario step shapes with 100% branch coverage of the original functions;
then add the new cases: SSE exclusion, 304 contract, id-token normalisation for client ids, the
three scenarios, intended scenario diff accepted, unintended scenario diff rejected. Stdlib
runner with a bare `python3`; `python-cross` shard.

**Equivalence:** flag OFF — zero diffs on every new probe and scenario. Flag ON — zero diffs for
all reconciled games; the flagged scenario must match on both sides (feed 409, widget row
fallback). Note the flag-on comparison only runs in full in Layer 4; this layer's flag-on run is
the smoke test that the extended probes are stable.

**Risks / rollback:** new probes may introduce nondeterminism (timestamps, ids); the noise floor
must pass before any report is trusted. Scenario writes create fresh rows on a shared DB — run
ids keep them distinguishable, never delete them. Rollback = revert PR; the harness is client
side only. **Merge safety: safe to merge with prod flag off.**

   function about to be changed/deleted with `--require-file/--require-function`.
2. **Removal:** delete the call and helper; no replacement write path. `POST /api/gamelog/<id>`
   keeps working exactly as before for its clients — TeamLog rows and the response are unchanged.
   Three guards keep the transition safe (all with exact `assertNumQueries`):
   - An unknown legacy event name still returns 400 and writes no rows: the endpoint validates
     names against the existing table in `gameevents/service/legacy.py` before
     `create_gamelog_once`, sharing the table with the projector rather than copying it.
   - Cross-endpoint idempotency survives: `GameEventsAPIView.post` checks `GameLogSubmission`
     as well as `GameEvent.client_id`, so a v1 op retried on the canonical endpoint is a no-op.
   - Mixed games cannot silently diverge: a v1 POST to a game with a `source=v2` event is
     refused with 409 before writing rows, and `append_submission` starts event (and therefore
     projected row) sequence after the largest existing `TeamLog.sequence`, so a row-only game
     that moves to v2 cannot collide. Tests cover both directions.

**Equivalence:**
- Flag OFF: every probe zero-diff **except** the declared intended diffs
  `v1-shadow-write:read-feed` and `v1-shadow-write:read-liveticker` where applicable — a new v1
  game no longer has events, so its feed falls back to `legacy_feed()` (`events: []`, `cursor: 0`,
  row-derived ETag). Reason: that is the point of removing the shadow write. All other probes and
  scenarios must be zero-diff, and the intended paths must be listed in `--intended` (Layer 3
  made scenario intended diffs possible). **P5, approved 2026-11-26** (§11): this is the one place
  where a flag-OFF comparison is not strictly zero-diff. The rehearsal applies Layers 5 and 6
  together, so the source=v2 discriminator from L6 is live in the cand build.
- Flag ON: zero diffs for every reconciled **v2** game; no v2 write path is touched. The recorded
  flag-ON run is the Layer 4 one (`phase2-l4-on`); it was **not re-run** after the flag-off revert
  at this layer. Layers 5 and 6 ship together in **one release**: the cand build for the gameday
  rehearsal contains both the shadow removal and L6's `source=v2` discriminator. A flag-ON run of
  L5 alone would characterize an intermediate build that is never released, so the joint
  rehearsal (§8.3), not a separate L5 flag-on report, is this layer's gate.

**Query counts:** v1 POST loses the shadow queries and the watermark aggregate — pin the lower
number; no count grows.

**Risks / rollback:** a client still relying on the v1 feed's event list would see it empty (the
declared intended diff); the public widget is unaffected because it reads rows. Partial revert
would restore the helper without the call — revert the whole PR. Reverting L5 on its own restores
shadow writes but **cannot restore the events for games played while they were absent**; there is
no backfill (§10 decision 3). Layers 5 and 6 are therefore shipped and rolled back as one unit:
on a failed rehearsal revert L6 first, then L5, and restore the env flag in every environment. The
layer is merged only after the user's gameday rehearsal on the agent stage confirms the event
path is stable.

**Merge safety: MERGE ONLY AFTER GAMEDAY REHEARSAL.** Include the rehearsal evidence in the PR body.

## 9. Hard-spot designs

**9.1 No `Gameinfo.event_source` migration.** The 2026-10-28 architecture uses `event_source` as
the per-game owner field, but it does not exist (`gameevents/models.py:8-10`) and adding it would
break the shared-DB ref/cand model (roadmap:38). Use the existing `GameEvent.source`: presence of
a `source=v2` event means the log owns the game; otherwise rows own it. `needs_reconciliation`
and the absence of a projection remain the existing escape hatches. If the user later insists on
a boolean/enum column, that is a new migration (`0006`), an `agent-ref` rebuild is impossible
against the same DB, and a **second DB copy plus a second ref container** is mandatory —
**recommended against** (**P2, approved 2026-11-26**).

**9.2 Cutover discriminator.** `feed.py:95-107` and `liveticker_service.py:105-112` filter on
`source=v2`; shadow-only games (`append.py:601`) are legacy for reads even though their events
are kept as audit. Layer 2's report provides the counts before any code changes. This is what
makes "events truth for v2, the accepted legacy games unchanged" executable without a schema
field (**P7, approved 2026-11-26**).

**9.3 Intended diffs.** The harness normalises ETag values, so validator shape differences are
not comparable; the 200↔304 contract is. Scenario diffs were previously always fatal
(`runner.py:157`); Layer 3 fixes that so Layer 5 can declare exactly one reason. Every intended
diff must name the probe/step, the path, and the decision that permits it; the report prints them
separately. No intended diff is allowed in Layers 1–4.

**9.4 ADR authority.** Roadmap §4.3–4.5 are final; Q1's "Leon — default in force" wording is
superseded, not reopened. The ADR names the maintainer as owner and is **Accepted
2026-11-26** (**P1, approved 2026-11-26**); Leon's Q1 sign-off is explicitly no longer required.
